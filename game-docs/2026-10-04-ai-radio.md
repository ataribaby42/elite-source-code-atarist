# AI ship radio

The Atari and Amiga versions each implement AI radio independently in
`asm/ai_comm.m68`. There are seven sets of ten messages. All use the existing
communications queue, receipt sound, ID formatting, recipient blink and viewport
renderer. Existing station message IDs 0–39 and station permission rules remain
unchanged; AI texts occupy IDs 40–109.

## Events

| Sender | Trigger | Recipient and text set |
| --- | --- | --- |
| Trader | First peaceful encounter within the player's scanner range with an eligible recipient | Cautious greeting to a pirate or wanted player; otherwise a friendly greeting to a trader or Clean player |
| Pirate | First valid combat target, or a changed target | Threat to the player or targeted AI ship |
| Neutral pirate | First encounter with the player after the existing Scramble ID mechanism has granted a truce | Friendly pirate greeting to the player |
| Thargoid | First valid combat target, or a changed target | A predefined unreadable transmission to the player or targeted AI ship |
| Police Viper | First valid combat target, or a changed target | Police threat to the player or targeted AI ship |
| Trader | First eligible player missile launch against it, or first survived positive laser/missile hit during its lifetime in the bubble | Protest addressed to the attacker |

Trader greetings require cruising or flying towards the planet and no anger
towards the player. Launching, docking, fleeing, fighting, removed and exploding
traders do not greet. A pirate's truce applies only to the player: it
can greet the player while fighting a different AI ship. That greeting and the
combat threat are separate events, each with its own 50% chance.

Only Thargoids send alien transmissions; Tharglets remain silent. Constrictors,
Cougars, stations, escape capsules, missiles and other special/non-ship objects
do not inherit ordinary ship messages from their faction field. Police messages
require both a Viper hull and the police role. Bounty hunters do not get police
messages.

Scanner range is the existing `radar_range`, inclusive. The observer runs after
the ship's ordinary AI logic, including while the player is viewing an in-flight
UI page. It does not send messages while docked or after game over.

## Trader greeting recipients

The first matching rule determines the recipient pool and text set:

1. If the player is Offender or Fugitive, choose between the player and the
   eligible AI pirates. Use the cautious set. With no pirates, choose the player.
2. If the player is Clean and there are eligible pirates, choose only among
   those pirates. Use the cautious set.
3. If the player is Clean and there are no eligible pirates, choose between the
   player and other eligible traders. Use the friendly set. With no other
   traders, choose the player.

Each individual recipient has equal weight, including the player when eligible.
An active player Cloaking Device suppresses all new radio, including AI-to-AI
greetings. Scramble ID changes only the printed player identity. If no eligible
recipient remains, the trader retains its greeting opportunity until one becomes
available. Once an eligible event is attempted, a silent roll or cooldown
suppression consumes it as before.

Recipient selection scans the entire active bubble, including ships beyond the
player's scanner range; the sending trader still needs to be within scanner
range. A recipient must be a living ordinary human ship with the required
pirate/trader faction. The sender, removed/exploding/abandoned ships, aliens,
special mission hulls and non-ship objects are excluded. Recipient selection
does not change either ship's combat target or other gameplay state.

The existing 50% transmission/text roll happens first. On success, recipient
selection uses the same independent cosmetic RNG with equal contiguous buckets
and rejection of the incomplete tail. This avoids modulo bias and low-bit
alternation for two candidates. A pool with one candidate needs no extra draw.

## One attempt per event

Outside the sender's cooldown, each event has exactly a 50% chance to send a
message, with ten equally likely variants on success. A failed roll consumes
the event. Greetings and protests are attempted once per ship lifetime.
Threats are attempted on a new valid target;
remaining on that target or changing between attack and evasive manoeuvres does
not retry. Losing a target and subsequently acquiring one is a new event.

Targets are tracked by a 32-bit object-lifetime serial, not by a reusable slot
pointer or printable registration. Reusing a target slot therefore counts as a
new ship, even if it has the same displayed ID. The two reserved values represent
the player and no target. Allocation, object creation after parent copies, removal
and whole-bubble clearing reset the relevant transient state. Commander saves and
model-data headers do not contain these fields.

The separate 16-bit cosmetic generator has a full-period cycle. Outcomes 65520
through 65535 are rejected; modulo 20 gives ten silent outcomes and ten text
variants. The complete accepted cycle has 32,760 silent events and 3,276 events
for each of the ten texts. It never advances gameplay, registration or station
message RNG state.

## Per-ship transmission cooldown

Each object slot has a transient `radio_cooldown` word. A successful AI radio
receipt sets it to 50 game frames, approximately three seconds at normal speed.
The main object loop subtracts one each frame until it reaches zero, including
off-screen ships and in-flight UI pages while the simulation runs. Pausing the
game pauses this counter; no hardware-clock conversion is used.

All AI message sets share the sender's cooldown. An event during cooldown is
consumed silently, without a random draw, a beep or a deferred retry. A failed
50% roll does not start a cooldown. Different ships can transmit independently.
Resolving a protest recipient never transfers the cooldown to the attacker.
Combat, missile launch hostility, Scramble ID truces and mission decisions are
not gated by radio availability. Station messages and the shared seven-second
queue timer retain their existing rules.

Allocation, creation after parent copies, removal and whole-bubble clearing
reset the counter. It is excluded from model headers and commander saves,
together with the other cosmetic radio fields.

## Active Cloaking Device

While the player's Cloaking Device is active, the AI observer and hit-protest
hook return before consuming events or drawing random numbers. The common AI
send/delivery helpers and shared queue also reject new receipts, including
AI-to-AI traffic. No receipt beep or new cooldown is generated. Existing ship
cooldowns continue counting game frames. After uncloaking, currently eligible
greetings/targets can be observed normally; a protest requires a new qualifying
hit or missile launch. Suppressed transmissions are never stored for replay.

Already received messages remain in the queue and follow its normal display and
expiry rules. Station messages are also suppressed while cloaked, and cargo
ejection incurs neither a legal-status penalty nor a station warning. Combat,
missile provocation and docking-permission rules remain separate from radio
suppression. Details are in [Cockpit communications](2026-10-04-comm-messages.md).

## Damage and identities

Protests have one shared opportunity: an eligible successful player missile
launch against the trader, or its first survived positive weapon hit. Launching
can trigger the protest before any damage, even if ECM later destroys the
missile. Python traders can protest without changing their fleeing behaviour or
defensive weapons. Launch and docking scripts, invincible objects and special
mission hulls remain excluded from the launch reaction.

For the damage trigger, fractional shield damage counts; zero damage,
invincibility, lethal hits and collisions do not. A silent roll or an event
outside scanner range still consumes the opportunity. A later missile impact,
another launch or further ticks of a Beam/Military burst cannot retry it.

Laser protests use the actual shooter. Missiles retain a launch-time snapshot of
the shooter's displayed registration and an explicit player-recipient flag. An AI
shooter disappearing or its slot being reused before impact cannot redirect the
protest. A missile without a known owner does not generate a misaddressed reply.

Pirate and Thargoid IDs stay `??-???`. A scrambled player ID is hidden using the
existing formatter. Messages addressed to the player pulse the recipient ID in
the engine colour, including anonymous player IDs; anonymous AI recipients do not
blink. Queued identities are snapshots and cannot change after receipt.

The existing pirate truce rule is preserved: eligible ordinary pirates may become
neutral when the player has both Scramble ID and Fugitive status. Radio reads the
resulting `pirate_truce` field; it never performs another hostility roll, modifies
a target, changes the legal record or alters mission/spawn rules.
The combat system cancels the targeted pirate's existing truce when the player
successfully launches a missile at it; radio only observes that change.

## Shared queue and display

The shared queue still holds three messages. New arrivals append at the bottom;
when full they immediately evict the oldest entry, also in UI. AI and station
messages have the same queue priority. Every successful receipt requests the
existing short communication beep, subject to normal sound settings. Failed
50% rolls do not beep.

The oldest entry expires every seven seconds spent in 3D. UI pauses this shared
timer. Messages draw only in the 3D viewport and use the existing word wrapping
and logical coordinates for framed, wide, hires and interlaced modes. Death,
new/load game, hyperspace/galactic jumps and docking retain their existing queue
clearing rules.

## Validation

`native_ai_radio.py` exercises the linked 68000 routines: the complete RNG cycle,
all 70 variants, legal-status greetings, failed-event suppression, AI/player
targets, target loss and slot reuse, mission/special-ship exclusions, damage,
actual missile launches/impacts, ID snapshots and the shared queue timer.

`native_ai_radio_parity.py` replays 44 actual encounters with radio observers
enabled and disabled. Each runs 90 AI steps. It compares all non-radio object
bytes and gameplay outcomes, including target selection, movement, damage,
registrations, random state, score, cash, legal status and mission state. Cases
include pirate attacks, random encounters, ordinary waves and mission states
`$15`, `$21`, `$41` and `$52`, with visible and scrambled player IDs.

`native_ai_radio_render.py` compares complete rendered screen checksums against
independently wrapped reference text, including mixed AI/player recipients,
hidden identities, UI suppression and every radio text category. Existing station
communications, spawn, combat, Scramble ID, missile, shield-flash and audio suites
remain part of regression validation. GUI emulator tests use verified private
hidden desktops and private executable/configuration/disk copies.

The exact text variants are listed in each platform's `asm/comm.m68`, IDs 40–109.

The Amiga continuous-beam raster regression requires cycle-accurate emulator
timing: maximum-speed emulation produced a missing-pixel sample while the burst
state remained active; the complete 91-scenario suite passed with cycle accuracy.
The game renderer was not changed for this test. New radio screen comparisons
also passed in PAL, PAL without fast drawing, PAL wide, PAL hires and NTSC hires
interlaced wide configurations.
